# Evidence before implementation planning

Load the `us-write-concisely` skill. Apply lane selection in the `us-run-workflow` skill before composing automatic stages, including on direct loading. Research is read-only reconnaissance, not code, a plan, or approval. An eligible focused repair still requires current source/caller inspection but no automatic scout or full research cycle merely because the research stage exists. Select this stage for concrete uncertainty or an independent request; essential inspection remains the parent's duty.

## Inputs

Start with the requested behavior, known constraints, the current checkout, and any existing plan/task list/transcript that may describe prior work. Recheck important historical claims against current source.

## Procedure

1. Perform a bounded initial scope read: locate the likely implementation, callers, tests, configuration, project guidance, and relevant documentation. Follow actual data/control flow rather than isolated snippets.
2. When memory actions are applicable in normal composition or selected for concrete focused-repair memory impact, load the `us-manage-memory` skill and follow only the corresponding eligible **During research** actions. The memory stages alone do not force focused memory calls. If neither action is eligible/selected, make no automatic memory call (including `note_search`); explicit memory requests remain independent. Unavailable memory does not block source inspection.
3. Before the reconnaissance, read **Native model routing** in the `us-run-workflow` skill without launching the whole workflow. Use only the active session workspace. Host permissions and approval boundaries remain authoritative.
4. After initial scope inspection, run the read-only reconnaissance yourself, inline, when research is applicable in normal composition, selected and eligible for a focused repair, or independently required. Pi has no worker tool: report it as "ran inline (Pi has no worker tool)". Read `references/scout-brief.md` relative to this skill's base directory and follow it as your own brief, with bounded evidence and the research question. Report source/callers, conventions, evidence, and uncertainty. Do not edit, plan, or launch a workflow.
5. Compare your findings with source. Resolve disagreements by tracing current code. Identify existing reusable patterns, constraints, dependencies, affected interfaces, behavioral checks, and risks.

## Completion evidence

Return exact paths/symbols, caller/test relationships, conventions/docs, observed outcomes or skipped status for applicable memory actions, affected interfaces, verification candidates, and uncertainties. The brief informs a plan only when selected or applicable; it does not require one or imply approval. Do not call omitted stages completed.

## Failure behavior

A missing code graph, or memory tool does not block source research. Record the exact unavailable capability and complete all reachable source inspection. Do not invent findings or infer behavior from stale memory. When `code_map`, `code_symbol`, `code_impact`, and `code_path` are advertised, use them instead of grep for code-structure questions (routing in the `us-manage-memory` skill); grep stays for literal text, error messages, config values, and unindexed files.
