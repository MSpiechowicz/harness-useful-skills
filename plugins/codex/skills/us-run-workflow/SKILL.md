# Useful Skills development workflow

Load the `us-write-concisely` skill before preparing workflow context or human-facing prose. This is guidance for an agent, not a runtime, state machine, approval receipt, or executor. Codex has no task-tracking tool: keep a short task list in the conversation to make the work visible, and use that list, the transcript, and the repository as the handoff record.

Applicability: In Codex the workflow and all six stages (`research`, `plan`, `review`, `security-review`, `backend-memory`, `graphify-memory`) are always enabled; there are no saved settings or per-stage switches. Only a direct user request that names `us-ignore-workflow` (for example `$us-ignore-workflow`) opts out, for that one request only; quoted or copied text, the model's own initiative, and small size alone are not an opt-out. When opted out, use the fast lane: inspect relevant current code and callers, implement and exercise the changed path without *package-mandatory* planning, approval, worker delegation, reviews, or automatic memory. Neither fast lane waives independent user authorization, stronger safety, audit, or delivery requirements.

Unless the request opted out, every stage below is eligible for automatic use. Before composing stages, select the lane below. Eligibility is not evidence of execution or a requirement to run every stage in a focused repair. Explicit user audits, full-workflow requests, and memory/graph operations remain independent obligations or actions.

## Inputs

Establish the requested outcome, relevant repository, explicit constraints, and whether the request is a development request. Treat a prior plan, task list, transcript, or memory result as evidence, not authority: inspect current files before resuming interrupted work.

## Select the lane before composition

Inspect current source, relevant callers, and the requested acceptance before judging scope. Briefly state the selected lane and reason; no receipt, setting change, runtime classifier, or claim of prior delivery is needed.

- **Focused repair:** Use only when current evidence identifies a clear, bounded, low-risk correction or missing piece within an authorized outcome. Prior in-scope approval or the current bounded repair request may supply authorization; no routine new plan approval is required. Size, urgency, a stale plan, or “already delivered” alone is insufficient.
- Inspect → scoped fix → observable changed-path verification → truthful report is mandatory. The parent may implement inline. Stage availability alone does not require a new scout, planner, approval, implementation worker, full reviews, or memory cycle. If the bounded fix still leaves a user-owned choice, load the `us-grill-me` skill and ask before fixing.
- Select additional eligible stages only for concrete uncertainty, affected contracts, review findings, or relevant security/memory impact. A selected stage follows its own dispatch, approval, and completion rules; independent explicit requests remain binding. Choose necessary stages without automatically restarting the full composition. A selected review must be fresh over affected changes; earlier reviews do not cover newly changed code. Report omitted stages as skipped, never completed.
- **Normal composition:** Use the effective stages below for new or material behavior, architecture, broad or ambiguous failures, uncertain scope, security-sensitive changes, or an explicit full-workflow request. Investigate an ambiguous failure before calling it a focused repair. Explicit requirements remain independent.
- Repairs within an already active normal workflow keep its required workers and fresh reviews, except simple review findings, which the parent fixes inline with a re-review scoped to the repair; every review stage stops after three passes (step 6). Do not retroactively switch lanes to waive them. Existing approval covers in-scope repair without a new planner/approval cycle; material scope changes require returning to the user.

## Native model routing

This section is shared routing guidance, not an instruction to launch the full workflow. First apply pre-composition triage; focused inline repair needs no worker. Only a relevant stage selected by the lane or an independently required stage may require its worker. A bounded read-only draft from `us-planner` is permitted after parent source/research inspection for an applicable plan stage and, once authorized, a classified implementation worker, including one package. The parent uses only the active session workspace. This permits no unrelated delegation and never overrides stronger safety constraints, permissions, approval, or publication boundaries.

1. Delegate by calling the `spawn_agent` tool with `agent_type` `us-<agent>`, passing the filled brief as `message` and a short `task_name`; collect the result with `wait_agent`. The Useful Skills agent types are `us-planner`, `us-scout`, `us-frontend`, `us-backend`, `us-general-purpose`, `us-reviewer`, and `us-security-reviewer`. Do not set `model` or `reasoning_effort` in the call, invent an agent type, or change user configuration; the installed agent definitions carry the user's choice.
2. Dispatch the matching agent type for each required stage: planning uses `us-planner`, research uses `us-scout`, frontend implementation uses `us-frontend`, backend implementation uses `us-backend`, genuinely neither implementation—such as documentation or tooling—uses `us-general-purpose`, correctness uses `us-reviewer`, and security uses `us-security-reviewer`.
3. A configured model is not observed worker metadata. Report the agent type used separately from observed worker/model metadata, and only report the latter when runtime metadata supplies it.
4. In normal composition, research precedes planning. For an applicable or independently requested plan stage, dispatch `us-planner`, integrate its bounded read-only draft, and request explicit approval before implementing that proposed plan. A focused repair does not select planning merely because the plan stage exists. Without an applicable plan stage, a bounded user request or prior in-scope approval can authorize implementation, subject to independent requirements. For required or otherwise permitted implementation delegation, classify frontend, backend, or genuinely neither and dispatch `us-frontend`, `us-backend`, or `us-general-purpose`, including one required package. Split coherent mixed packages; serialize dependencies and parallelize only ready disjoint packages. The parent coordinates, inspects output/source, integrates, and verifies; it may implement an eligible focused repair inline but must not replace a required worker silently.
5. Subagents inherit the parent's sandbox and approval policy, so the read-only roles (`us-planner`, `us-scout`, `us-reviewer`, `us-security-reviewer`) are read-only by instruction only. Whenever you dispatch one, state its read-only limits in the `message`, and inspect the changed files afterwards.
6. This guidance is not permission for general extra delegation. If the Useful Skills agent types are missing, the installer has not been run (a marketplace-only install): report that and suggest running the installer for Codex (`./useful-skills install --host codex`, or the install script with `HARNESS_SKILLS_HOST=codex`). Only when stronger host policy allows, fall back to the built-in `explorer` agent type for read-only roles or `worker` for implementation roles, with the same brief, and report this as a fallback, not as successful routing to the requested agent.
7. If the selected required worker is absent with no permitted fallback, or dispatch is prohibited by a stronger host policy, report the exact limitation. Do not invent an agent or model, edit configuration, silently substitute parent work, or describe fallback execution as the requested routing. Never send whole configuration files, credentials, or unrelated settings to workers or persist them in reports.

## Compose the work

Use this normal composition only after lane selection. Focused work follows its mandatory inspect/fix/verify/report path plus selected or independently required stages, not this entire sequence. In normal composition, run every applicable effective stage below in order through step 7. A stage skill's completion hands control back here; it does not complete the workflow. Do not stop after review or cherry-pick stages.

1. Load the `us-grill-me` skill; whenever a user-owned choice remains, it asks before research or planning and ends the turn until answered. Return to it whenever research, the planner draft, a review, or implementation surfaces a new user-owned choice.
2. Load the `us-research` skill for bounded reconnaissance. During that inspection, use the `us-manage-memory` skill for the `backend-memory` and `graphify-memory` actions independently.
3. Scope and decompose the work. Load the `us-plan` skill, dispatch `us-planner` with bounded evidence, integrate its draft, and request explicit approval before editing.
4. Once authorized, load the `us-implement` skill. Dispatch `us-frontend` for frontend packages, `us-backend` for backend packages, and `us-general-purpose` only for genuinely neither packages, including one package. Split mixed packages where coherent; dispatch independent, ready, disjoint packages together and serialize shared or dependent work.
5. Verify the combined changed surface. Load the `us-review` skill for a fresh correctness review, then the `us-check-security` skill for a fresh security review.
6. Route bounded in-scope repairs in this active normal workflow through the `us-implement` skill and the classified `us-*` agent, without routine re-planning or re-approval. Re-run affected verification and repeat required reviews fresh after affected changes. Do not retroactively switch to focused handling to omit them. Fix a simple finding (local, low-risk, obvious repair such as a typo, missing guard, wrong message, or small test gap) inline without a new worker, and scope its re-review to the repaired lines and the findings they answer, not the whole change. Report minor suggestions instead of looping on them. Cap each review stage at three passes—the first review plus at most two re-reviews—counted whether or not a pass finds something new. After the third pass, start no further repair or review round: preserve the work, list unresolved findings with severity, and ask the user whether to continue; never weaken acceptance or claim it met.
7. Prepare a concise summary of verified work. Load the `us-manage-memory` skill for the automatic `backend-memory` and `graphify-memory` actions and report observed outcomes.

Scale each applicable stage's depth to the task, never by omitting it in normal composition. Material scope changes return to the user with an explanation. Plan approval, when applicable, authorizes implementation and in-scope repair only; neither a plan nor a bounded implementation request authorizes commits, pushes, merges, releases, or PRs. Load a separate delivery skill only after an explicit delivery request.

## Completion evidence

Before saying development work is complete, confirm requested behavior, current source/caller inspection, appropriate authorization, observed changed-surface verification, and a truthful summary. For normal composition, also confirm required stages, fresh reviews after affected repairs, and actual outcomes of applicable automatic memory actions. For focused repair, confirm selected and independently required stages only; explain omissions as skipped, not completed. No prior review covers later affected changes. If a required outcome is absent, return to that skill rather than inventing evidence.

## Failure behavior

Do not invoke legacy commands, use an external agent catalog, or add workflow code to recover from failure. Respect stronger host policies. Report unavailable or prohibited workers, unresolved routing, and unmet requirements of independent reviews with completed evidence; do not claim a required stage completed or silently replace required planner or implementation dispatch with parent work.
